# StegoCode: Browser-Based Steganography and Visual Machine-Readable Code Research

StegoCode is two things at once:

1. **A working browser application** — client-side tools for protected image
   steganography and for standalone Version 1 QR generation and scanning. No build step,
   no framework, no server, no dependency installation.
2. **An ongoing research and learning project** — a structured investigation into how far
   machine-readable visual codes can be pushed toward human-meaningful appearance, and how
   much data can be hidden inside ordinary images.

Both halves matter. The applications work today; the research programme is being built
around them without replacing them.

---

## Quick start

Open any of these files in a modern browser:

| File | What it does |
| :--- | :--- |
| `stego_app.html` | Hide and recover a UTF-8 message in a lossless image |
| `qr_app copy.html` | Generate a Version 1 QR symbol from scratch and scan QR images or camera frames |
| `qr_app.html` | QR Studio using the `qrcodejs` library for generation |

Camera scanning needs a secure context (HTTPS or `localhost`) and browser camera
permission. Generation in `stego_app.html` and `qr_app copy.html` needs no network access.

## Existing functionality

### Protected image steganography

`stego_app.html` embeds a UTF-8 payload in the RGB least-significant bits of a lossless
image, with real integrity protection rather than a sentinel terminator.

- **RGB least-significant-bit insertion** — bit 0 of each channel, which changes a channel
  value by at most ±1.
- **Alpha channel skipped** — the A byte is never read or written, avoiding transparency
  side effects.
- **UTF-8 payload handling** — via `TextEncoder` / `TextDecoder`, the decoder in strict
  fatal mode so corrupted bytes can never be shown as plausible text.
- **`STG` magic bytes** — `0x53 0x54 0x47`, so a decode either finds a packet or fails.
- **Version information** — a format version byte, currently 1.
- **Payload length framing** — a two-byte big-endian byte count, so the payload is
  self-delimiting.
- **CRC-16 integrity** — CRC-16/CCITT-FALSE over the header and payload.
- **Block-level protection** — the packet is split into 3-byte groups.
- **CRC-8** — each group gains a CRC-8 byte (CRC-8/SMBUS).
- **GF(256) parity** — two parity symbols per block, over the field generated by
  `0x11d`, giving a systematic (6, 4) Reed–Solomon code with minimum distance 3.
- **One-symbol-per-block repair behaviour** — a block with exactly one damaged symbol is
  repaired; a clean block is reported as clean, not as a repair.
- **Rejection of ambiguous or multiply corrupted blocks** — two damaged symbols in one
  block are rejected outright. A wrong payload is never returned.
- **Lossless image requirements** — JPEG and other lossy paths destroy the payload; the
  output is always PNG.
- **Browser-only operation** — no upload, no server, no network request of any kind.

### QR Studio

`qr_app copy.html` contains a standalone Version 1 QR encoder written from scratch, plus
scanning.

- **21 × 21 module symbols** — Version 1, and only Version 1.
- **UTF-8 byte mode** — mode indicator `0100`.
- **Mode indicator** — written explicitly in the bit stream.
- **Byte-length indicator** — the 8-bit byte-mode character count.
- **Reed–Solomon error-correction codewords** — generated over GF(256) by polynomial
  division, using the QR generator polynomials for 7, 10, 13, and 17 ECC codewords.
- **Finder patterns** — three 7 × 7 nested-square markers.
- **Separators** — the one-module light ring around each finder.
- **Timing patterns** — alternating modules along row 6 and column 6.
- **Quiet zone** — four modules, applied as canvas padding.
- **Fixed dark module** — at row 13, column 8.
- **Format information** — BCH(15,5)-protected, written to both standard copies.
- **All eight QR masks** — every mask built and scored, not just one.
- **ISO-style mask penalty evaluation** — all four penalty rules summed, lowest score
  selected.
- **Canvas output** — rendered at an integer module size, centred.
- **PNG download** — via `canvas.toDataURL('image/png')`.
- **Version 1 capacity constraints** — payloads that do not fit are rejected with an
  explicit message naming the limit, rather than producing an invalid symbol.
- **`jsQR` used for scanning** — for both uploaded images and live camera frames.
- **QR generation itself does not use a QR-generation library.** The encoder is entirely
  in-repo. `qr_app.html`, by contrast, generates through `qrcodejs`; the two pages are
  otherwise nearly identical.

#### Version 1 byte-mode capacity

| Level | Approximate recovery | Maximum UTF-8 bytes |
| :--- | :---: | ---: |
| L | 7% | 17 |
| M | 15% | 14 |
| Q | 25% | 11 |
| H | 30% | 7 |

These are UTF-8 **bytes**, not characters. A message of ten emoji is 40 bytes.

### QR is not encryption

**QR is a data representation and transport mechanism, not a cryptographic one.**

Encoding a string as a QR symbol provides no confidentiality, no authenticity, and no
integrity guarantee beyond Reed–Solomon error correction. Anyone with a scanner reads it.

Cryptographic payloads — encryption, signatures, signed URLs, identity assertions, tamper
evidence — may later be carried *inside* a QR symbol or inside a steganographic payload,
but cryptography and QR encoding must remain conceptually separate in the code, the
documentation, and any claim made about the project. Nothing in this repository currently
provides cryptography.

The same applies to the LSB codec: a hidden payload is **hidden, not protected**. Anyone
who knows the `STG` format can read it. Hiding is not security.

## Verification

Both implementations were exercised end-to-end by loading their actual source into Node
with a minimal DOM stub and testing the codec and encoder functions directly:

- **Protected steganography — 23/23 checks passed**: exact UTF-8 round trip, CRC-8 and
  CRC-16 matching the standard check values (`0xF4`, `0x29B1`), single-symbol repair at
  every position in a block, rejection of multiply damaged blocks, and header guards.
- **Version 1 QR encoder — 59/59 checks passed**: module role counts (192 finder/separator,
  10 timing, 30 format, 1 dark module, 208 data/ECC), generator-polynomial roots, zero
  Reed–Solomon syndromes at every ECC level, all 32 format codewords BCH-valid and
  round-tripping to the right ECC level and mask, structural validation of all 32 ECC ×
  mask matrices, an independent re-extraction of the codeword bitstream from each, exact
  capacity enforcement (17/14/11/7 bytes), and correct minimum-penalty mask selection.

That harness was deliberately **not** committed. There are no tests in the repository, and
establishing a repeatable in-project validation procedure is the `A0` milestone.

## Limitations

| Dimension | Standard QR code | StegoCode (spatial LSB) |
| :--- | :--- | :--- |
| Visual distortion | High — monochrome grid artefacts | Effectively zero — below perceptual threshold |
| Compression resilience | High — Reed–Solomon ECC | Low — lossy compression destroys bit 0 |
| Camera recapture | Native — corner finder targets | None — requires spatial synchronisation |
| Format requirement | Any visual medium | Lossless raster only (PNG, BMP, lossless WebP) |

Additional limitations:

- The LSB codec must be used through a lossless image path. JPEG, resize, crop, screenshots,
  print-and-capture, and social-media recompression all destroy the payload.
- The protected decoder repairs at most one damaged symbol in each six-symbol block. It
  gives no guarantee against arbitrary corruption, and there is no interleaving, so damage
  concentrated in one region is worse than the same amount spread out.
- QR Version 1 capacity is intentionally small, and only Version 1 is generated. Numeric,
  alphanumeric, Kanji, multi-version, and alignment-pattern support are all absent.
- Successful digital decoding does not guarantee camera decoding. These are separate claims.
- Scanner behaviour differs between implementations; a single decoder's result is not
  evidence of general readability.
- `qr_app.html` and `qr_app copy.html` load `jsQR` (and, for the former, `qrcodejs`) from
  public CDNs. The applications never transmit payloads, images, or camera frames, but the
  CDN operators see the page load, and the pages do not work without network access.
- No cryptography, no machine learning, no optimiser, and no literature review.

The full list, with mechanisms, is in [`docs/LIMITATIONS.md`](docs/LIMITATIONS.md).

## Research programme

The project is split into three research routes. All three are documented; only Route A is
active.

```text
Route A — standards-compatible artistic QR
          How closely can a valid QR symbol resemble a target logo while
          ordinary QR scanners still decode it?
          Constraint: standard QR compatibility is required.

Route B — custom logo-readable optical code
          How much visual freedom is gained by abandoning QR compatibility
          while keeping practical camera decoding?
          Constraint: a dedicated StegoCode scanner is allowed.

Route C — image steganography
          How much machine-readable information can be hidden inside an
          ordinary image while preserving human-visible appearance?
          Constraint: the carrier is the image signal, not an optical pattern.
```

The distinction that matters:

```text
Route A: visually stylized but overt optical code
Route B: custom logo-shaped optical code
Route C: data hidden in the image signal itself
```

### Current research state

```text
Current route:            Route A
Current stage:            documentation / research foundation
Next experiment:          A1 — Mask/ECC Visual Similarity Baseline
A1 implementation status: NOT STARTED
```

**There is no target-logo optimiser in this repository, and none was added during the

Route A's progression:

```text

```

## Guiding principle

StegoCode should evolve from a collection of interesting browser experiments into a
reproducible research project without sacrificing the implementations that already work.

Preserve first. Measure second. Optimize third.

The immediate long-term research direction:

> Determine how far a standards-compatible QR code can be visually transformed toward a
> target logo while retaining reliable machine readability.
